# Phase 13 — Observability

## Lesson 1：Log、Metric、Trace 的区别与设计

本课正式开始 Phase 13。我们先不安装 LangSmith，也不急着修改代码。第一步是明确：**投资 Agent 需要观察什么、不同观测数据解决什么问题，以及如何把这些要求映射到现有的 LangGraph 工作流中。**

这一步看似偏理论，但它决定了后续观测系统的数据结构。如果一开始就接入平台，却没有定义需要记录的内容，最后很容易出现这样的情况：页面上有很多执行记录，但发生故障时，仍然无法解释为什么失败、时间花在哪里、最终投资结论是怎样形成的。

### 一、先明确 Phase 13 的工程目标

根据你提供的项目计划，Phase 13 的核心问题是：

> 当 Agent 执行复杂任务时，我们如何知道它做了什么、耗费了什么、在哪一步失败，以及为什么得出最终结果？

原始项目计划要求加入 Tracing、Metrics 和 LangSmith，并验收 Graph、Node、Tool、LLM 调用及错误的可观测性。

修订后的计划进一步明确了十节课，从观测数据模型、执行关联标识，逐步推进到节点追踪、LLM 与工具调用、Token 与成本、结构化日志、业务结果关联、敏感信息保护和故障诊断。

因此，Phase 13 不是简单地给程序增加几条日志，也不是以接入某个第三方平台为终点。

#### 1.1 本阶段最终要回答的问题

假设你运行：

```powershell
.\.venv\Scripts\python.exe .\scripts\e2e_real_workflow.py --allow-paid-llm-calls --approve --ticker AAPL
```

这是此前已经验证过的端到端工作流：使用真实 LLM，但市场和数据 Provider 采用 MOCK。

当工作流完成后，你应该能够回答以下问题：

| 问题 | 需要的能力 |
|---|---|
| 这次执行是否成功？ | 可靠的执行状态与错误记录 |
| 这次执行经过了哪些 Graph 节点？ | Graph 和 Node Trace |
| 哪个节点耗时最长？ | 节点级耗时数据 |
| 调用了多少次 LLM？ | LLM 调用追踪与指标 |
| 哪次 LLM 调用失败了？ | 调用级错误记录 |
| 模型调用耗时多少？ | 延迟指标 |
| 消耗了多少 Token、产生了多少模型费用？ | Token 与成本统计；前提是能够获得可靠的使用量数据 |
| 最终投资结论与哪些研究步骤有关？ | Trace 与业务结果关联 |
| 为什么这次研究失败或结果不完整？ | 错误、执行轨迹和业务状态的联合诊断 |

注意：这张表是本项目需要达到的目标，不代表当前代码已经具备全部能力。

#### 1.2 本课的交付

本课先建立三个基础概念：

1. **Log：** 记录发生了什么。
2. **Metric：** 用数值衡量系统运行情况。
3. **Trace：** 记录一次执行经过了哪些步骤，以及步骤之间的关系。

然后，我们会结合现有代码，确定后续实现的边界。暂时不引入新的依赖，不修改生产代码，也不进行需要真实 LLM 付费的测试。

### 二、Log：日志，回答“发生了什么？”

#### 2.1 日志是什么？

Log 是一条描述某个事件的记录。

例如，投资 Agent 开始执行 AAPL 研究任务时，可以记录：

```text
event=research_started
ticker=AAPL
run_id=abc123
```

某个节点失败时，可以记录：

```text
event=node_failed
node=risk_analysis
error_category=llm_error
run_id=abc123
```

以上是示意格式，并不是当前项目已经产生的实际日志。

一条有价值的日志通常需要包含：

- **时间：** 事件什么时候发生？
- **事件类型：** 开始、成功、失败，还是重试？
- **执行标识：** 这条记录属于哪次执行？
- **发生位置：** 哪个 Graph、节点、工具或组件？
- **结果或状态：** 成功、失败、跳过，还是部分成功？
- **错误信息：** 如果失败，发生了什么？

具体字段会根据事件类型有所不同，不必要求所有日志都包含完全相同的字段。

#### 2.2 为什么不能只用 `print()`？

你当前的 E2E 脚本会打印执行信息，也会生成 `report.md` 和 `run_summary.json`。这些输出很有用，但它们与统一的运行日志并不等价。

`print()` 可以帮助开发者观察程序输出，却缺少日志系统通常提供的能力，例如：

- 统一的日志级别：DEBUG、INFO、WARNING、ERROR。
- 统一的结构化字段。
- 按执行标识筛选相关事件。
- 将异常与具体节点和执行关联。
- 根据运行环境控制日志输出方式。

需要特别区分：**不是说 `print()` 没有价值，而是它不应该成为正式应用唯一的诊断机制。**

例如：

- `INFO`：研究任务已开始。
- `WARNING`：某个非关键数据源不可用，工作流决定继续。
- `ERROR`：风险分析节点最终失败。
- `DEBUG`：开发环境下记录更详细的节点处理信息。

日志级别应该表达事件的重要程度，而不是简单地把所有信息都记下来。

#### 2.3 投资 Agent 应该记录哪些事件？

对本项目而言，初步可以将日志分为四类。

| 类别 | 典型事件 | 目的 |
|---|---|---|
| 工作流事件 | Graph 开始、结束、失败 | 确认整体执行状态 |
| 节点事件 | 节点开始、成功、失败 | 定位故障位置 |
| 外部调用事件 | LLM 或 Provider 调用失败、重试 | 诊断外部依赖问题 |
| 业务事件 | 风险分析完成、投资决策生成、报告生成 | 将技术执行与业务流程关联 |

这里有一条重要边界：

**日志应该记录足以诊断问题的信息，但不应该默认记录完整 Prompt、完整模型响应、API 密钥或全部投资研究材料。**

详细的敏感信息处理会在 Lesson 13.8 中专门讨论。现在先建立正确的原则：可观测性不等于无差别地记录所有数据。

### 三、Metric：指标，回答“系统运行得怎么样？”

#### 3.1 指标是什么？

Metric 是对系统运行情况进行量化的数值。

例如：

```text
research_runs_total = 100
research_failures_total = 3
llm_calls_total = 250
llm_latency_seconds = 2.4
```

这些数字同样只是示意。

与日志不同，Metric 通常用于观察一段时间内的整体表现，例如：

- 有多少次研究任务？
- 失败率是多少？
- 平均执行时间是多少？
- 哪类节点的延迟最高？
- LLM 调用量是否异常增加？
- 单次研究任务的模型成本是否超出预算？

#### 3.2 三种常见的指标类型

实际工程中，常见的指标包括 Counter、Gauge 和 Histogram。

| 类型 | 含义 | 投资 Agent 示例 |
|---|---|---|
| Counter | 只增不减的累计计数 | 累计失败次数、LLM 调用次数 |
| Gauge | 某一时刻的数值，可以升降 | 当前正在执行的任务数量 |
| Histogram | 对一系列数值进行分布统计 | 节点耗时、LLM 调用延迟 |

这里不需要立即引入 Prometheus 或其他指标平台。首先要理解的是，不同问题需要不同的统计方式。

举例来说，假设今天执行了 1,000 次 LLM 调用：

- `llm_calls_total` 可以告诉我们调用了多少次。
- 延迟 Histogram 可以帮助我们了解调用耗时的分布。
- 失败计数可以告诉我们发生了多少次调用失败。

如果只记录一条“LLM 调用成功”的日志，就很难直接回答这些聚合问题。

#### 3.3 为什么平均耗时还不够？

假设有两组研究任务：

- A 组平均耗时 10 秒。
- B 组平均耗时 10 秒。

仅凭平均值，我们无法判断两组任务是否具有相同的性能表现。

A 组可能几乎都在 9～11 秒内完成；B 组则可能大多数在 3 秒内完成，少数任务却耗时几分钟。

因此，除了平均耗时，还需要根据实际诊断需求关注：

- P50：第 50 百分位耗时。
- P95：第 95 百分位耗时。
- P99：第 99 百分位耗时。

这些分位数有助于观察慢请求，但前提是我们有足够的观测样本，并采用了正确的统计方式。

对当前项目来说，我们暂时不必马上建设完整的性能监控平台。先保证能够采集可信的执行耗时，并且可以关联到具体的研究任务和节点。

#### 3.4 成本指标有什么特殊性？

投资 Agent 会调用 LLM，因此成本是重要的运行指标。

但不能把调用次数直接等同于费用。

不同模型的价格可能不同，输入 Token 和输出 Token 的计价也可能不同；缓存 Token、供应商计费规则等因素也可能影响成本。

所以，后续需要区分：

1. **调用数量：** 调用了多少次模型。
2. **Token 使用量：** 输入和输出分别消耗多少 Token。
3. **成本估算：** 根据模型、价格配置及使用量估算费用。
4. **实际计费：** 供应商最终记录的费用。

如果模型接口没有返回可信的 Token 使用量，我们就不能假装知道精确用量；如果价格配置过期，成本估算也可能不准确。

这部分会在 Lesson 13.5 深入实现。

### 四、Trace：执行轨迹，回答“这次任务具体经历了什么？”

#### 4.1 Trace 的核心思想

Trace 是一次执行的关联轨迹。它不只是记录若干事件，而是把属于同一次执行的操作组织起来，并呈现它们之间的关系。

在现代可观测性系统中，Trace 通常由多个 Span 组成：

- **Trace：** 一次完整的执行轨迹。
- **Span：** 轨迹中的一个操作或执行区间。
- **Parent Span：** 另一个 Span 的父操作。
- **Child Span：** 在父操作内部发生的子操作。

每个 Span 通常包含开始时间、结束时间或持续时间、操作名称、执行状态，以及必要的关联属性。

举个例子，假设一次 AAPL 投资研究任务依次完成市场研究、估值、风险分析、投资决策和报告生成。

概念上的 Trace 可以是：

```text
Trace: AAPL Investment Research
│
├── Graph: application
│   │
│   ├── Node: market_research
│   │   ├── Tool: market_data_provider
│   │   └── LLM: research_summary
│   │
│   ├── Node: valuation
│   │   └── LLM: valuation_analysis
│   │
│   ├── Node: risk_analysis
│   │   └── LLM: risk_analysis
│   │
│   ├── Node: investment_decision
│   │   └── LLM: investment_decision
│   │
│   └── Node: report_generation
│       └── LLM: report_generation
```

这是为了说明层级关系的简化示意图，不代表当前项目实际的节点拓扑或 LLM 调用数量。真实轨迹必须依据运行时发生的操作生成，不能靠预先画好的流程图冒充。

#### 4.2 Trace 与 Log 的区别

假设风险分析节点中的一次 LLM 调用失败。

**日志可能记录：**

```text
event=llm_call_failed
node=risk_analysis
error_type=TimeoutError
run_id=abc123
```

它告诉我们：风险分析中的某次 LLM 调用超时了。

但我们还可能需要知道：

- 这次调用属于哪一个风险分析节点执行？
- 风险分析节点本身耗时多久？
- 超时前已经完成了哪些操作？
- 这次调用失败后，是否发生重试？
- 整个研究任务最后是成功、部分成功，还是失败？

Trace 通过组织相关的执行区间，帮助回答这些问题。

两者并不是互相替代的关系：

- Log 记录离散事件及其上下文。
- Trace 组织一次执行中的操作及其因果、层级关系。
- Log 可以带有 `trace_id` 或 `span_id`，从而定位到具体轨迹或执行区间。

**一个很重要的区别：有 Trace 不代表有完整日志；有日志也不代表有完整 Trace。**

#### 4.3 Trace 与 Metric 的区别

假设某次研究任务耗时 45 秒。

Trace 可以帮助你分析这 45 秒花在了哪里：

| 操作 | 耗时 |
|---|---:|
| 市场研究节点 | 8 秒 |
| 估值节点 | 12 秒 |
| 风险分析节点 | 15 秒 |
| 报告生成节点 | 10 秒 |
| 总计 | 45 秒 |

这张表只是演示数据。

Metric 则可以统计许多次执行的耗时，例如研究任务的 P95 耗时是否从 40 秒上升到了 70 秒。

因此：

- **Trace 关注一次执行的内部细节。**
- **Metric 关注一组执行的统计特征。**

两者配合使用，既能发现系统整体变慢，也能进一步定位某次执行为什么变慢。

#### 4.4 一个容易忽略的问题：时间不等于因果关系

假设两个研究节点并行执行：

```text
Graph
├── Financial Research
└── Industry Research
```

两个节点的开始和结束时间可能交错。不能简单地把日志按时间排序，就认为它们一定是严格的先后依赖关系。

Trace 的父子关系和执行关联有助于保留结构信息；对于并行执行，还需要正确处理节点间的关联，不能假设所有操作都组成一条直线。

这一点对于 LangGraph 尤其重要，因为图执行可能涉及分支、并行节点、条件路由、子图和人工审批。

### 五、把三种能力放到同一个故障中

我们用一个具体场景串联三个概念。

**场景：** AAPL 研究任务最终失败，错误发生在风险分析阶段。

#### Log 应该告诉我们什么？

- 风险分析开始了。
- 某次 LLM 调用发生超时。
- 重试策略是否触发，以及重试结果。
- 风险分析最终成功还是失败。
- 整个研究任务最终如何结束。

#### Metric 应该告诉我们什么？

- 最近一段时间风险分析的失败次数。
- 风险分析的平均耗时和 P95 耗时。
- LLM 调用超时的频率。
- 单次研究任务的调用量与成本。

#### Trace 应该告诉我们什么？

- 失败的风险分析属于哪次完整研究执行。
- 风险分析之前执行了哪些节点。
- 具体是哪次 LLM 调用超时。
- 失败操作与后续重试、最终失败之间的关系。
- 整个执行链路的主要耗时分布。

这三个视角解决的是不同问题。对于本项目，目标不是从中挑选一种，而是让它们能够互相补充。

### 六、回到你的源码：目前已经具备什么？

前面的概念必须与现有实现对应起来。否则，课程就会变成与项目脱节的理论介绍。

我检查了你上传的 Phase 12 源码。以下结论基于这份源码快照，而不是对你本地运行环境的实时检查。

#### 6.1 已有基础一：结构化错误信息

文件：

`app/application/errors.py`

当前实现包含 `ApplicationErrorDetail`，其字段包括：

```python
class ApplicationErrorDetail(TypedDict):
    stage: str
    code: str
    category: ErrorCategory
    retryable: bool | None
    handling_owner: str
    exception_type: str
    message: str
```

这已经是很好的工程基础。

例如，当某个阶段发生错误时，系统可以记录：

- 错误发生在哪个阶段。
- 错误属于什么类别。
- 错误是否可重试。
- 哪个组件负责处理。
- 异常类型和消息是什么。

而且，`make_error_detail()` 会根据异常类型进行分类。

但是需要区分：

**结构化错误信息不等于完整的 Observability。**

它解决的是错误如何被分类和表达的问题，并不自动提供完整的节点耗时、LLM 调用轨迹、指标统计或跨组件执行关联。

#### 6.2 已有基础二：Application Graph 的执行状态

文件：

`app/application/graph.py`

当前 Application Graph 已经使用 `execution_status` 表示执行生命周期，并通过 `error_details` 保存结构化错误。

这意味着系统已有部分业务执行状态和失败诊断信息。

后续我们不应该为了 Observability 再造一套与之冲突的错误体系。

正确的方向是：

1. 保留现有错误分类。
2. 在合适的执行边界采集观测信息。
3. 将观测记录与已有错误信息关联。
4. 避免把业务状态、错误分类和日志系统混为一谈。

例如，`execution_status="failed"` 是业务执行状态；日志中的 `event="node_failed"` 是一次观测事件。两者可能相关，但语义不同。

#### 6.3 已有基础三：Thread ID 和 E2E Run ID

文件：

- `app/graph/runtime.py`
- `scripts/e2e_real_workflow.py`

当前代码已经有两种重要的标识。

`build_thread_config(thread_id)` 会把 `thread_id` 放入 LangGraph 的 `configurable` 配置中，用于关联带有持久化状态的工作流执行。

E2E 脚本则会生成 `run_id`，并使用它构造本次执行的输出目录和 `thread_id`。同时，它会写入 `run_metadata.json`，保存模型、数据 Provider 模式、执行标识及产物路径等信息。

这意味着我们不必从零开始设计所有执行标识。

不过，后续必须进一步明确：

- `run_id` 用来关联什么？
- `thread_id` 用来关联什么？
- 业务任务标识是否需要独立存在？
- 恢复执行时，哪些标识应该保持不变？
- 每次恢复操作是否还需要单独的执行尝试标识？

这些问题会在 Lesson 13.2 中正式解决。现在先不要提前修改它们。

#### 6.4 当前缺少什么？

在这份源码快照中，我没有发现已经形成统一体系的标准日志、指标和 Trace 实现。

更准确地说：

| 能力 | 当前源码中观察到的情况 |
|---|---|
| 结构化错误分类 | 已有 |
| Graph 执行状态 | 已有 |
| Thread ID | 已有 |
| E2E Run ID | 已有 |
| E2E 元数据与执行产物 | 已有 |
| 统一结构化日志体系 | 尚未发现完整实现 |
| Graph / Node 执行耗时追踪 | 尚未发现统一实现 |
| LLM / Tool 调用级 Trace | 尚未发现统一实现 |
| 统一 Metrics 采集与统计 | 尚未发现完整实现 |
| 业务结果与完整 Trace 关联 | 尚未发现完整实现 |

这里的“尚未发现”是针对本次检查的源码快照，不代表系统在所有运行环境下绝对没有相关能力。

**本课的工程结论：现有错误处理、执行状态和 E2E 元数据应该被 Observability 复用，而不是被替换。**

### 七、为这个项目建立正确的观测模型

现在，我们可以把三个概念整合为一张设计图。

```text
Investment Research Task
│
├── Logs
│   ├── Graph started
│   ├── Node started
│   ├── LLM call failed
│   └── Graph completed / failed
│
├── Metrics
│   ├── Research execution count
│   ├── Research failure count
│   ├── Node latency distribution
│   ├── LLM call count
│   └── Token usage and cost estimates
│
└── Trace
    └── One execution's operation hierarchy
        ├── Graph execution
        ├── Node execution
        ├── LLM calls
        └── Tool / Provider calls
```

三者需要通过一致的关联信息建立联系。

例如，当你在日志中发现某次风险分析失败时，可以定位到对应 Trace；打开 Trace 后，能查看风险分析节点及其子操作；如果发现大量任务的风险分析耗时上升，再通过 Metrics 判断这是个别异常还是普遍趋势。

这就是我们希望建立的可观测性基础。

#### 7.1 我建议采用的实施原则

结合你的项目当前阶段，我建议遵循以下原则。

**原则一：先明确数据模型，再选择工具。**

先定义需要记录的事件、字段和关联关系，再决定是否引入 LangSmith 或其他平台。

**原则二：本地诊断能力不能完全依赖第三方平台。**

即使将来使用 LangSmith，我们仍然应该保留必要的执行标识、结构化错误和可诊断的业务结果。

**原则三：不以“产生了日志”作为验收标准。**

真正的验收应该证明：执行结束后，可以查询到正确的节点轨迹、调用耗时和错误关联信息。

**原则四：观测代码不能破坏业务执行。**

例如，观测系统暂时不可用时，不应该无条件导致整个投资研究任务失败。观测记录本身也需要明确的异常处理边界。

**原则五：控制数据量和敏感信息。**

我们不需要把所有研究内容、完整 Prompt 和模型响应全部写入日志，才能实现有效诊断。

## Lesson 2：Run ID、Thread ID 与 Business Task ID

本课进入实际工程设计。上一课我们明确了 Log、Metric 和 Trace 分别解决什么问题；现在要解决一个更基础的问题：

**当系统中存在多次研究执行、失败重试、人工审批和中断恢复时，我们如何准确识别每一次执行，并把相关日志、Trace 和最终投资报告关联起来？**

这不是简单地给程序增加几个 UUID。标识符设计不正确，会直接影响后续的故障诊断、恢复执行、成本统计和审计能力。

本课遵循现有项目计划：先理解标识符的职责，再检查 Phase 12 的实现，最后明确设计方案和验收标准。暂不直接修改生产代码。

---

### 一、先理解三个不同的问题

假设用户提交一个任务：

> 研究 AAPL，完成基本面分析、估值、风险分析，形成投资决策和研究报告。

系统执行过程中可能出现以下情况：

1. 第一次执行时，风险分析节点失败。
2. 系统保留了 LangGraph 的状态。
3. 用户或系统随后恢复执行。
4. 恢复后生成投资决策和报告。
5. 用户过几天再次要求研究 AAPL，启动一项新的研究任务。

如果所有这些活动都只使用一个标识符，就很难准确表达它们之间的关系。

因此，我们需要先区分三个概念：

| 标识符 | 回答的问题 | 主要职责 |
|---|---|---|
| `run_id` | 这是哪一次执行运行？ | 关联一次运行产生的日志、Trace 和运行产物 |
| `thread_id` | 这是哪条持久化的工作流状态线程？ | 定位 LangGraph 保存和恢复的状态 |
| `business_task_id` | 这是哪一项业务任务？ | 关联业务请求、相关执行及最终业务结果 |

这三个标识符服务于不同的概念，不能因为它们都能使用 UUID，就把它们当成同一回事。

需要强调：上表是我们正在建立的目标设计模型。具体到当前项目，哪些标识符已经存在、是否需要新增字段，以及它们在恢复场景中如何变化，都必须以源码和实际执行语义为依据。

---

### 二、Run ID：识别一次运行

#### 2.1 基本定义

`run_id` 用于识别一次运行，并将这次运行产生的记录关联起来。

例如：

```text
run_id = 896b27455b6a
```

当日志中出现：

```text
event=graph_started
run_id=896b27455b6a
```

以及：

```text
event=graph_failed
run_id=896b27455b6a
```

我们就可以知道这两条记录属于同一个运行标识。

不过，**`run_id` 究竟代表多大范围，必须由应用明确规定**。它不是一个天然具有固定语义的 LangGraph 概念。

常见的设计选择包括：

- 一次外层应用程序执行。
- 一次完整的研究工作流。
- 一次 Graph 调用。
- 一次重试尝试。

这些范围可能不同。因此，不能只生成 UUID，就认为执行关联设计已经完成。

#### 2.2 当前项目中的 `run_id`

检查文件：

`scripts/e2e_real_workflow.py`

当前代码在 E2E 脚本开始时生成：

```python
run_id = uuid.uuid4().hex[:12]
```

随后使用这个 ID 构造产物目录，并写入 `run_metadata.json`。

当前元数据还包含：

```python
metadata = {
    "run_id": run_id,
    "thread_id": thread_id,
    "ticker": ticker,
    # 其他运行元数据
}
```

这说明当前 `run_id` 的明确用途是：**标识一次 E2E 脚本运行及其相关产物**。

脚本还会使用同一个 `thread_id` 先执行工作流，再在人工审批中断后恢复执行。因此，当前 `run_id` 不是严格意义上的“每次 `graph.invoke()` 调用的唯一标识”。

这一区别很重要。

当前设计可以帮助我们找到某次 E2E 测试的报告、结果、元数据和 Checkpoint 数据库，但不能据此断言未来所有 Graph 调用都已经具有独立的运行标识。

#### 2.3 本项目需要怎样的 Run ID？

后续需要区分两个层次：

**层次 A：研究执行级别**

代表一次完整的研究执行活动，包含研究输入、工作流推进以及最终产物。

**层次 B：单次调用级别**

代表某一次具体的 Graph 调用，或一次恢复执行调用。

例如：

```text
研究执行
│
├── Graph 调用 1：执行到人工审批中断
│
└── Graph 调用 2：提交审批结果并恢复执行
```

如果只使用一个 ID 表示两个层次，就会模糊运行记录的范围。

因此，后续设计需要明确：
- 研究执行的标识如何生成和保存。
- 每次 Graph 调用如何被识别。
- 重试或恢复时，哪些标识保持不变，哪些需要变化。

我们暂时不新增字段，因为 Lesson 13.3 和后续上下文传播设计还会影响最终的数据结构。

---

### 三、Thread ID：识别持久化工作流线程

#### 3.1 Thread ID 解决什么问题？

在 LangGraph 中，配置中的 `thread_id` 主要用于标识与 Checkpointer 关联的工作流线程。

它不是简单的日志标签，而是持久化工作流状态的重要定位信息。

例如：

```python
config = {
    "configurable": {
        "thread_id": "e2e-aapl-896b27455b6a"
    }
}
```

当工作流使用 Checkpointer 时，同一线程可以用于读取和延续此前保存的状态。

这正是 Phase 9、Phase 10 及后续错误恢复设计中需要的能力。

#### 3.2 当前项目中的实现

文件：

`app/graph/runtime.py`

当前代码：

```python
def build_thread_config(thread_id: str) -> RunnableConfig:
    """Build the runtime configuration required for checkpointed execution."""
    if not isinstance(thread_id, str) or not thread_id.strip():
        raise ValueError("thread_id must be a non-empty string")

    return {
        "configurable": {
            "thread_id": thread_id,
        }
    }
```

这段代码做了两件事：

1. 拒绝空字符串或无效类型的 `thread_id`。
2. 将有效的 `thread_id` 放入 LangGraph 约定的 `configurable` 配置中。

它没有创建新的研究任务，也没有生成 `run_id`。它的职责是构建 Checkpointer 执行所需的配置。

这是一种良好的职责划分。

#### 3.3 为什么恢复时不能随意更换 Thread ID？

假设初次执行使用：

```text
thread_id = research-aapl-001
```

工作流执行到人工审批节点时中断，并将状态保存到 Checkpointer。

如果恢复时改成：

```text
thread_id = research-aapl-002
```

系统就会转而定位另一个线程，而不是原先保存状态的线程。

在常规的 Checkpointer 恢复流程中，这意味着系统无法通过新 ID 找到原线程的检查点，因而不能按预期恢复原执行。

正确的做法是：**恢复同一条持久化工作流时，使用原来的 `thread_id`。**

但这不代表 `thread_id` 永远不能变化。

如果用户发起的是一项真正独立的新研究任务，通常应该创建新的线程，而不是错误地复用旧线程。

#### 3.4 一个关键边界

`thread_id` 不应直接等同于股票代码。

例如：

```text
thread_id = AAPL
```

这个设计可能导致多次独立的 AAPL 研究任务共享同一个线程标识。

如果它们本来应该拥有各自独立的工作流状态，就会增加错误地读取、恢复或覆盖关联状态的风险。

更稳妥的设计是为独立工作流生成唯一标识，并在业务元数据中单独保存股票代码。

当前 E2E 脚本使用的：

```python
thread_id = f"e2e-{ticker.lower()}-{run_id}"
```

就是一种测试执行隔离方式。它将股票代码用于识别任务对象，同时通过运行标识区分不同的 E2E 执行。

需要注意：这只是当前 E2E 脚本的实现，不代表未来生产环境必须使用完全相同的 ID 格式。

### 四、Business Task ID：识别一项业务任务

#### 4.1 为什么还需要业务任务标识？

假设用户今天要求研究 AAPL。

第一次执行失败，第二次执行通过重试完成。过几天，用户又要求重新研究 AAPL。

从股票代码来看，这三次活动都是 AAPL；但从业务角度看，它们并不一定是同一项任务。

我们需要回答：

- 哪些运行属于同一项业务任务？
- 某次失败和后续成功是否属于同一项任务？
- 一份研究报告是由哪项业务任务生成的？
- 同一项业务任务的执行历史在哪里？

因此，我们需要一个独立的 `business_task_id`。

它用于标识**业务层面的一项研究任务，而不是某一次技术执行**。

#### 4.2 举个例子

假设用户先提交任务 A：

> 研究 AAPL，分析估值、风险并生成报告。

系统生成：

```text
business_task_id = task-001
```

第一次运行失败：

```text
business_task_id = task-001
run_id = run-001
```

系统重试：

```text
business_task_id = task-001
run_id = run-002
```

两次运行属于同一项业务任务，但它们是不同的运行尝试。

几天后，用户重新发起一项独立的 AAPL 研究任务：

```text
business_task_id = task-002
run_id = run-003
```

虽然股票代码相同，但新任务有自己的业务标识。

示意关系如下：

```text
Business Task: task-001
│
├── Run: run-001  → Failed
│
└── Run: run-002  → Completed
                    └── Research Report

Business Task: task-002
│
└── Run: run-003  → Completed
                    └── Research Report
```

这里的 ID 都是示意值。

需要注意：业务任务是否应该在重试后保持同一个 ID，取决于业务定义。对于同一项任务的技术重试，通常应该保持；如果用户明确提交了一项新的研究请求，通常应该生成新的业务任务标识。

#### 4.3 Business Task ID 应该由谁创建？

这取决于未来应用的调用方式。

如果研究 Agent 被封装在 Web API 后面，业务任务标识可以由应用服务层在接收任务时生成。

如果是命令行工具，也可以由命令行入口创建。

如果未来由其他 Agent 或调度系统提交任务，则需要明确由哪个组件负责生成和传递标识。

关键原则是：

**业务任务标识应该由明确的业务边界管理，而不是让每个 Graph 节点各自生成一个。**

否则，市场研究节点、估值节点和风险分析节点可能分别生成不同的任务 ID，导致无法将它们关联到同一项研究任务。

另外，股票代码不适合充当业务任务 ID，因为同一只股票可以对应无数项独立研究任务。

---

### 五、三个标识如何协同工作？

现在，我们将三个概念放到一起。

#### 5.1 推荐的目标模型

| 维度 | `business_task_id` | `thread_id` | `run_id` |
|---|---|---|---|
| 所属层次 | 业务层 | 工作流持久化层 | 执行观测层 |
| 标识对象 | 一项业务任务 | 一条持久化工作流线程 | 一次执行尝试 |
| 主要用途 | 关联研究请求与最终业务结果 | 关联 Checkpoint 状态 | 关联一次执行的日志、Trace 和耗时 |
| 重试时是否保持不变 | 同一业务任务通常保持 | 恢复原线程时保持 | 新的执行尝试生成新的 ID |
| HITL 恢复时是否保持不变 | 保持 | 保持 | 按新的执行调用生成新的 ID |
| 新建独立研究任务时 | 新 ID | 通常新 ID | 新 ID |

**这是我建议后续采用的目标模型，不是当前源码已经完整实现的行为。**

其中需要特别解释两点。

第一，HITL 恢复时，`thread_id` 应该保持不变，因为我们需要继续使用原有的持久化工作流状态。

第二，本课程建议将 `run_id` 定义为一次应用层执行尝试的唯一标识。对于初次执行和恢复调用，可以使用不同的 `run_id`，但通过 `business_task_id` 将它们关联起来。

这种设计有利于分别分析每次执行的耗时、错误和调用情况，同时保留完整的业务任务历史。

#### 5.2 为什么不直接让三个 ID 相等？

如果这样设计：

```text
business_task_id = thread_id = run_id
```

那么一次执行失败后，系统就很难清楚地表达：

- 同一业务任务经历了多次执行。
- 同一条持久化工作流可能被多次调用。
- 每次执行产生了不同的日志和 Trace。

三个标识符即使碰巧使用相同的字符串，也不能因此视为同一概念。

工程设计中应该首先明确各自的职责，再决定它们之间的关联方式。

#### 5.3 为什么还需要考虑恢复场景？

我们之前已经实现了 LangGraph 的持久化和 HITL 恢复。

例如：

```text
第一次调用 Graph
       │
       ▼
执行研究节点
       │
       ▼
到达人工审批节点
       │
       ▼
保存 Checkpoint 并中断
       │
       │ 等待审批
       ▼
第二次调用 Graph
       │
       ▼
使用原 thread_id 恢复
       │
       ▼
继续执行并生成报告
```

如果将来把所有调用都视为同一个 `run_id`，就难以区分每次调用的耗时和失败。

如果每次恢复都生成新的 `thread_id`，又会影响原有 Checkpoint 的定位。

如果恢复后生成了新的 `business_task_id`，就可能把同一项业务任务的前后执行拆散。

因此，三个标识符必须分别管理，不能用一个标识符同时承担三种职责。

### 六、检查当前实现：哪些已经存在，哪些还没有？

结合你上传的 Phase 12 源码，可以得出以下结论。

| 项目 | 当前状态 | 说明 |
|---|---|---|
| `run_id` | 已有，但语义仍需完善 | E2E 脚本用它标识一次脚本运行及相关产物 |
| `thread_id` | 已有 | 用于构造 LangGraph 的持久化执行配置 |
| `business_task_id` | 在已检查的核心执行路径中尚未发现统一实现 | 需要进一步设计业务任务标识的生成、传递和保存 |
| 运行元数据 | 已有 | E2E 脚本记录模型、Provider 模式、执行标识及产物路径 |
| 多次执行的业务关联 | 尚未发现完整的统一实现 | 需要在后续课程中建立 |
| 每次 Graph 调用的独立观测关联 | 尚未发现完整的统一实现 | 需要结合 Trace 设计实现 |

这里不应该简单地认为“已有 `run_id`，所以不需要再做任何事情”。

**已有标识符只是基础；标识符的语义、生命周期和传播规则同样重要。**

### 七、为后续实现确定设计原则

为了避免后续课程不断修改标识符设计，我建议将以下原则作为 Phase 13 的工程约束。

#### 原则 1：业务任务与执行尝试分离

一次业务任务可以包含多次执行尝试。

```text
Business Task
    ├── Run 1
    ├── Run 2
    └── Run 3
```

失败重试不应该无故创建新的业务任务。

#### 原则 2：恢复同一工作流时保留 Thread ID

只要业务意图是继续同一条持久化工作流，就应该使用原来的 `thread_id`。

新建独立研究任务时，再根据业务设计决定是否创建新的工作流线程。

#### 原则 3：每次执行尝试都可以被独立诊断

不同执行尝试应该能够分别查询：

- 开始和结束时间。
- 最终状态。
- 失败信息。
- 主要耗时。
- 相关的节点和外部调用。

因此，目标设计中，每次新的应用层执行尝试应拥有独立的 `run_id`。

#### 原则 4：标识符必须向下游传播

如果 Graph 知道 `business_task_id`，但节点日志中没有它，后续就难以从业务任务定位日志。

同样，如果 LLM 调用无法关联到所属运行，也很难诊断调用耗时和失败。

后续课程需要解决这种上下文传播问题，而不是让每个节点自行猜测或生成标识。

#### 原则 5：不要混淆 Checkpoint 与 Trace

Checkpoint 用于持久化工作流状态，支持恢复和延续执行。

Trace 用于描述执行操作之间的关系，帮助分析执行路径和耗时。

两者可以通过标识建立关联，但它们的目的不同，不能相互替代。

## Lesson 3：Node 与 Graph 的执行轨迹

本课开始把前两课的设计落到 LangGraph 的实际执行机制中。

本课目标不是简单地在每个节点前后增加 `print()`，而是建立一套可验证的执行追踪能力，让系统能够回答：

1. 一次 Graph 执行什么时候开始、什么时候结束？
2. 实际执行了哪些节点？节点按照什么顺序执行？
3. 每个节点开始和结束的时间是什么？
4. 每个节点执行了多久？
5. 哪个节点执行失败了？
6. 如果 Graph 在人工审批处中断，应该如何记录？
7. 如何区分节点的技术执行成功与节点返回的业务失败状态？

最后一个问题尤其重要。你的 Application Graph 已经有比较完整的错误处理机制，如果我们不理解现有设计就直接加追踪代码，很容易把业务失败误记为技术执行成功，或者把正常的 HITL 中断错误地记录为失败。

**本课的工程策略：先确定执行事件的语义，再设计采集方式，最后通过自动化测试验证实际产生的轨迹。**

### 二、为什么不能只记录最终 execution_status？

当前项目已经有 `execution_status`，包括：

- `running`
- `completed`
- `failed`
- `rejected`

而且 `finalize_application()` 会调用 `_terminal_execution_status()`，在最终输出边界规范化状态。

这很好，但它只能告诉我们最终执行状态，不能替代节点执行轨迹。

假设两次 AAPL 研究都返回：

```python
{
    "execution_status": "failed",
    "application_error": "Risk stage failed: ..."
}
```

第一种情况可能是风险分析中的 LLM 调用超时；第二种情况可能是风险分析返回的数据不符合预期契约。

即使最终状态相同，排查方法也可能不同。

同样，两个运行都成功，也不代表它们的性能相同。一次可能耗时 20 秒，另一次可能耗时 90 秒。

所以我们需要记录中间过程，而不是只观察最终结果。

#### 2.1 为每个节点定义执行事件

我们先设计最基本的事件集合：

| 事件 | 含义 |
|---|---|
| `graph_started` | 一次 Graph 调用开始 |
| `graph_completed` | 一次 Graph 调用正常结束 |
| `graph_failed` | Graph 调用因未处理异常而失败 |
| `graph_interrupted` | 执行因中断而暂停 |
| `node_started` | 一个节点开始执行 |
| `node_completed` | 一个节点正常完成技术执行 |
| `node_failed` | 一个节点发生未处理异常 |
| `node_interrupted` | 节点执行因中断而暂停 |

这些是我们拟定的观测事件，不是当前代码已经实现的事件名称。

还需要注意，事件名称本身并不够。每个事件必须有明确的语义，尤其是 `completed`、`failed` 和 `interrupted`。

例如，节点返回了一个包含 `execution_status="failed"` 的状态更新，但 Python 函数本身没有抛出异常。它到底应该被记录为 `node_completed` 还是 `node_failed`？

答案是：**取决于我们追踪的是技术执行状态，还是业务阶段状态。两者应该分别表达。**

后面会专门处理这个问题。

---

### 三、Node 执行状态与业务状态必须分开

这是本课最重要的设计点之一。

#### 3.1 技术执行状态

技术执行状态关注节点代码是否正常完成。

例如：

```python
def example_node(state):
    return {"value": 42}
```

如果节点正常返回，技术执行就是成功的。

如果节点执行时抛出未处理异常，技术执行就是失败的。

#### 3.2 业务阶段状态

业务阶段状态关注节点完成后，业务处理是否成功。

你的 `run_risk_stage()` 使用异常捕获与 `_failure_update()` 处理失败。在某些失败场景中，它不会把异常继续抛给 LangGraph，而是返回一个包含错误信息和 `execution_status="failed"` 的状态更新。

因此可能出现：

```text
技术执行：节点函数正常返回
业务执行：风险分析失败
```

这并不矛盾。

类似地，某个研究阶段可能完成了技术执行，但由于数据源不完整，返回的是降级结果。

如果我们把所有这些情况简单地记录成 `node_completed`，就可能遗漏重要的业务信息；如果因为业务状态为 `failed` 就认定节点发生了未处理异常，又会错误描述实际执行情况。

#### 3.3 推荐的数据模型

建议把节点追踪记录设计为至少包含以下信息：

| 字段 | 含义 |
|---|---|
| `event` | 事件名称 |
| `run_id` | 所属执行尝试 |
| `thread_id` | 所属持久化工作流线程，若已提供 |
| `node_name` | 当前节点名称 |
| `timestamp` | 事件发生时间 |
| `duration_ms` | 节点执行耗时，在结束事件中记录 |
| `execution_outcome` | 技术执行结果 |
| `business_status` | 可获取时记录业务状态 |
| `error_type` | 发生异常时的异常类型 |

这只是当前课程的目标数据模型。我们还没有决定所有字段的最终名称，也不应该为了填满字段而伪造不存在的信息。

特别是：

- `execution_outcome` 不应直接复制 `execution_status`。
- `business_status` 不一定能从所有节点的返回值中可靠提取。
- `duration_ms` 应从实际计时结果计算，而不是根据节点顺序估算。
- `run_id` 和 `thread_id` 需要通过执行上下文传递，不能在每个节点中随意重新生成。

这些区分能避免观测系统与现有业务状态混淆。

### 四、如何采集节点轨迹？三种实现方式

理解了数据模型后，我们要选择实际的采集方式。

LangGraph 提供了多种观察执行过程的途径。对于你的项目，我们需要同时考虑节点名称、开始与结束时间、异常、HITL、中断恢复以及现有业务代码的稳定性。

#### 方案 A：在每个节点内部手动记录

例如：

```python
def run_risk_stage(state):
    started_at = time.perf_counter()

    # 原有风险分析逻辑
    ...

    duration_ms = (time.perf_counter() - started_at) * 1000
    ...
```

优点：
- 实现直观。
- 容易在节点内部补充业务信息。

缺点：
- 每个节点都要维护类似代码。
- 容易遗漏某个节点。
- 异常分支和提前返回可能导致记录不完整。
- 修改业务代码与观测代码的耦合度较高。

**结论：不采用这种方式作为顶层 Node 追踪的主要实现。**

节点内部仍然可以记录特定业务事件，但不应要求每个业务节点重复实现通用计时逻辑。

#### 方案 B：在 Graph 构建时包装节点

可以在 `builder.add_node()` 前后引入统一包装器，由包装器负责记录节点开始、结束、耗时和技术执行结果。

概念上：

```python
builder.add_node(
    "risk",
    instrument_node("risk", run_risk_stage),
)
```

这里的 `instrument_node()` 只是示意名称，目前项目中尚不存在这个函数。

优点：
- 能够明确知道包装的是哪个节点。
- 不需要在每个业务函数中重复计时逻辑。
- 可以针对节点返回值补充必要的业务状态信息。

缺点：
- 必须正确处理节点的输入、输出和运行配置。
- 需要正确处理异常及 LangGraph 的中断语义。
- 如果在包装器中捕获异常却不重新抛出，可能改变原有的错误处理行为。
- 如果把整个 State 复制进日志，可能泄露敏感信息或造成日志膨胀。

对于当前项目，这种方式有一定吸引力，但需要非常谨慎地处理异常和中断。

#### 方案 C：使用 LangGraph / LangChain 的运行事件与回调机制

LangChain 提供了回调接口和运行事件机制，LangGraph 也提供了流式执行接口，可以观察 Graph 及其内部操作的执行过程。

这种方案的主要优势是：

- 可以在业务节点之外观察执行。
- 有机会获取运行名称、执行标识、时间和状态等信息。
- 可以在后续扩展到子图、LLM 和工具调用。
- 能够减少在业务函数中插入通用观测代码的需要。

但不能仅凭接口存在，就假设它已经满足我们的全部要求。

我们仍然需要验证：

1. 当前项目使用的 LangGraph 版本实际产生哪些事件。
2. 如何可靠地识别顶层节点与子图内部节点。
3. 运行配置中的 `thread_id` 和其他上下文如何传递。
4. 节点返回业务失败状态时，事件如何表达。
5. HITL 中断时，是否会触发普通的结束或异常回调。
6. 如何保证回调异常不会破坏业务执行。

##### 我的选择：优先验证框架事件机制，再决定生产实现

我建议先通过一个极小的实验 Graph，验证当前依赖版本的事件行为。

如果事件机制能够稳定提供所需的节点生命周期信息，就优先使用框架提供的接口；如果某些关键信息无法可靠获取，再考虑在明确的边界补充包装器。

这样做不是为了多做实验，而是为了避免在生产 Graph 中引入一个错误处理语义不清楚的通用包装器。

**本课不应为了追踪而破坏现有的 HITL、Checkpoint 或错误恢复行为。**

### 五、Graph 级追踪与 Node 级追踪有什么区别？

我们前面重点讨论了节点，现在把视角提升到整个 Graph。

#### 5.1 Graph 级别记录什么？

一次 Graph 调用至少需要记录：

```text
graph_started
    |
    | 执行若干节点
    |
graph_completed
```

如果 Graph 因未处理异常失败，则记录失败终态；如果因人工审批等原因暂停，则记录中断状态。

一条 Graph 级记录可以设计为：

```json
{
  "event": "graph_completed",
  "graph_name": "application",
  "run_id": "run-001",
  "thread_id": "thread-001",
  "started_at": "2026-10-26T06:00:00Z",
  "ended_at": "2026-10-26T06:00:45Z",
  "duration_ms": 45000,
  "execution_outcome": "completed"
}
```

这是示意数据，并非当前项目的真实执行记录。

实际实现时，时间字段应该使用统一的时间格式；耗时则应该通过单调时钟计算，而不是简单地用两个系统时间戳相减。

例如，Python 中可以使用：

```python
started_at = time.perf_counter()

# 执行需要测量的操作

duration_ms = (time.perf_counter() - started_at) * 1000
```

`time.perf_counter()` 适合测量时间间隔，不受系统时钟调整造成的影响。

如果还需要记录事件发生的绝对时间，可以另外使用 UTC 时间戳。

#### 5.2 一个容易忽略的边界：Graph 调用不一定等于完整业务任务

假设第一次调用 Graph 后，工作流在审批节点暂停。

此时 Graph 调用已经结束，但业务任务并没有完成。

之后，第二次调用 Graph，工作流从 Checkpoint 恢复并最终完成。

因此，可能出现这样的记录：

```text
Business Task: task-001

  Graph Invocation 1:
      outcome = interrupted

  Graph Invocation 2:
      outcome = completed

  Business Task:
      outcome = completed
```

这里需要严格区分三个层次：

- 单次 Graph 调用的执行结果。
- 持久化工作流的状态。
- 业务任务的最终结果。

在本项目中，不能因为第一次 Graph 调用结束，就把整个业务任务标记为完成。

#### 5.3 计时范围也必须明确

如果我们测量的是一次同步 `graph.invoke()` 调用的持续时间，那么：

- 首次执行到人工审批中断，记录首次调用耗时。
- 用户等待审批的时间，不属于首次 `invoke()` 的运行时间。
- 恢复调用的耗时，单独记录。
- 如果需要统计从任务创建到最终完成的总耗时，则需要另外计算业务任务生命周期。

这几个指标的含义不同，不能混用。

### 六、如何确定一次 Node 执行成功还是失败？

我们已经明确，技术执行结果和业务状态必须分开。现在进一步定义具体规则。

建议采用以下规则：

| 场景 | 技术执行结果 | 业务状态 |
|---|---|---|
| 节点正常返回，业务处理成功 | `completed` | `completed` |
| 节点正常返回，但业务阶段报告失败 | `completed` | `failed` |
| 节点正常返回，但结果为降级数据 | `completed` | `degraded` |
| 节点发生未处理异常 | `failed` | 视实际情况确定 |
| 节点因工作流中断而暂停 | `interrupted` | 通常尚未完成 |
| 节点没有执行 | 不应生成虚假的执行记录 | 不适用 |

这里的 `degraded` 是我们建议使用的观测语义，不代表当前所有节点都已经采用这个状态名称。

#### 6.1 为什么不能直接读取整个 State 来判断节点结果？

假设 `risk` 节点执行前，State 中已经存在某个历史错误。

如果包装器仅仅检查：

```python
if state.get("execution_status") == "failed":
    ...
```

那么即使当前节点执行成功，也可能被误记为失败。

类似地，如果节点返回的 `execution_status` 是 `running`，也不代表节点本身发生了技术错误。

因此，追踪器不能只依赖整个 State 的最终状态来判断当前节点的技术结果。

正确的做法是：

1. 从执行机制获取当前节点的执行结果。
2. 从节点返回值中提取能够可靠判断的业务结果。
3. 将两者分别记录。
4. 对无法可靠判断的业务状态保留未知值，而不是猜测。

这也是为什么我不建议立即编写一个只检查 `execution_status` 的通用包装器。

### 七、Phase 13.3 的实现方案

综合前面的分析，我建议按以下顺序实现。

#### 第一步：验证当前依赖版本的事件行为

创建一个独立的最小 Graph，包含：

- 一个正常返回的节点。
- 一个抛出异常的节点。
- 一个通过条件边提前结束的路径。

观察框架实际产生的事件，确认是否能够识别节点名称、执行开始和结束，以及异常信息。

这一步不调用真实 LLM，也不修改生产 Graph。

#### 第二步：验证 HITL 中断行为

使用一个带有人工审批中断的最小 Graph，检查：

- 中断时产生哪些事件。
- 中断是否会被普通异常回调误判。
- 恢复执行时事件如何表现。
- 同一 `thread_id` 下的两次调用能否分别识别。

这一步很重要，因为当前项目已经具有 HITL 与 Checkpoint 恢复能力。

#### 第三步：建立统一的 Graph / Node 追踪接口

根据前两步的实验结果，确定生产实现方式。

无论最终采用回调、事件流还是节点包装器，都应该有统一的数据语义，至少能够表达：

- Graph 名称。
- Node 名称。
- 开始和结束事件。
- 执行耗时。
- 技术执行结果。
- 可可靠获取的业务状态。
- 关联执行标识。
- 必要的异常信息。

#### 第四步：接入 Application Graph

在确认观测机制不会改变业务执行语义后，将其接入顶层 Graph。

此时还不要求完整追踪 LLM 和工具内部操作，因为那是 Lesson 13.4 的重点。

#### 第五步：通过自动化测试验收

测试必须检查实际产生的观测数据，而不只是检查 Graph 的返回值。

例如，测试需要证明：

- 正常节点确实产生开始和结束记录。
- 节点耗时是非负数。
- 失败节点能够关联到异常。
- 条件路由不会虚构未执行节点的记录。
- HITL 中断不会被错误记录为普通成功。
- 观测失败不会无条件破坏业务执行。
